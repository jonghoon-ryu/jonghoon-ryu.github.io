🧭 CS:APP Companion: Reading Computer Systems: A Programmer's Perspective with This Library

Note What this is: a map from every chapter and lab of Bryant and O’Hallaron’s Computer Systems: A Programmer’s Perspective (CS:APP, 3rd edition, 2015) to the chapters of this library that prepare for it, run alongside it, or go further. It contains no material from the book: section topics are named in our own words, so keep the book open beside this page. How to use it: find the CS:APP chapter you are about to read, skim the before column, read the book with the alongside chapters open, then do the lab. Links open the library’s chapters in this reader; links marked ↗ open a separate page.

Tip Three things before you start. (1) Prefer the North American edition: the practice problems of the Global Edition were rewritten by another publisher and are known to contain many errors. (2) The labs are the heart of the course. CMU publishes self-study versions of all of them, with handouts and autograders, on the book’s site (csapp.cs.cmu.edu, Labs), and the CMU 15-213 lectures that follow the book are online. (3) Do each chapter’s practice problems before looking at their solutions at the end of the chapter.

✅ How to study one CS:APP chapter

  1. Before: read the 🟢 chapters, or only their summaries and cheat sheets if you know the topic.
  2. Read the book one section at a time, with the 📖 chapters open. Do every practice problem on paper first.
  3. Run it. Type the book’s small examples, compile them with gcc -Og -S, and compare your .s file with the book’s listing. GCC 13 often produces different code from the book’s GCC 4.8; working out why is excellent practice. T3 explains the options and X1, Step 9 the two assembly syntaxes.
  4. Lab. Start it as soon as the chapter’s core sections are read; it will send you back to the book.
  5. Further: the 🔵 chapters, once the lab is done.

Important Syntax. CS:APP, the x86-64 tab and the fold-out listings of the C++ course all use AT&T syntax (movq %rsp, %rbp, source first), which is also what GCC, objdump -d and GDB print by default. Intel’s manuals and some tools use Intel syntax (mov rbp, rsp, destination first); X1, Step 9 shows both side by side, and objdump -d -M intel or GDB’s set disassembly-flavor intel switch to it.

🧪 Data Lab. Bit puzzles written with a small set of operators and no control flow (for example, absolute value or “is this a power of two” without if). Helps most: Ch. 6’s bitwise steps and X5’s shifts. Tip: write each answer as a truth table for the sign bit first; most puzzles are about how the sign behaves.

Chapter 3 — Machine-Level Representation of Programs

The x86-64 tab was written to accompany it: X1–X10 cover the same ground as the book’s Sections 3.1–3.7, in the same syntax, with every example run on a current CPU.

🧪 Bomb Lab. A program with six “phases”; each wants a secret input, and the only way to find it is to read the machine code. Prepare with X7 (jump tables appear in one phase), X9 and T6’s GDB steps. Tip: set a breakpoint on the function that “explodes” before anything else, and use x/s to look at strings the code compares with.

🧪 Attack Lab. Exploit two programs with buffer overflows: first by injecting code, then with return-oriented programming against a non-executable stack. Prepare with X9 (where the return address lives), X1 (instruction encoding, for writing bytes by hand) and Ch. 49 (why the defences exist). Tip: draw the stack frame of the vulnerable function, byte by byte, before writing any exploit string.

Chapter 4 — Processor Architecture

The book: a small instruction set, Y86-64, then a sequential processor, pipelining, hazards and forwarding, described in a hardware control language.

X17 is the library’s chapter for this one: the Y86-64 instruction set and its encodings, an assembler, a sequential processor printed stage by stage, and a five-stage pipeline in C++ with stalling, forwarding, the load/use hazard, branch prediction and the cost of ret, checked against the sequential processor with random programs. It describes the processors in C++ rather than the book’s HCL, so read the book for HCL and the hardware view, and X17 to run and trace the same ideas. Related: X7’s branch-prediction measurement, and Inside the Arm Architecture ↗ for RISC versus CISC and instruction encodings.

🧪 Architecture Lab. Extend the Y86-64 processor and optimise a copy loop on it. Prepare with X17: its Try it yourself adds iaddq, the lab’s first task, to a sequential and a pipelined processor written in C++, and Step 10’s random-program test is a good way to check your own changes.

🧪 Cache Lab. Write a cache simulator that replays memory traces, then a matrix transpose with as few misses as possible. Prepare with the book’s Section 6.4 and Performance C++ ↗ (rows versus columns). Tip: for the transpose, work out on paper which elements of A and B map to the same set; most misses on the diagonal come from that.

O20 is this library’s virtual-memory chapter, written to go with this one: thirteen programs that show a process’s map, a virtual address turned into a physical frame, the page tables’ own memory, the TLB measured, demand paging, the zero page, copy-on-write, major faults, mmap of a file, how glibc’s malloc uses brk and mmap, overcommit and SIGSEGV. Read its Steps 1–4 with the book’s 9.1–9.6, Steps 6–10 with 9.7–9.8, and Step 11 just before the Malloc Lab.

🧪 Malloc Lab. Write malloc, free and realloc, judged on both speed and memory use. Prepare with the book’s Section 9.9, O20 Step 11, then Ch. 21; E6 ↗ Step 30 shows the simplest bare-metal allocator to compare with. Tip: write a heap checker (every block’s header matches its footer, no two free blocks are adjacent, every free block is on the list) before optimising; Ch. 45’s vector internals show the same discipline.

🧪 Proxy Lab. A web proxy: sequential first, then concurrent, then with a cache shared between threads. Prepare with O22, whose Step 8 is a small caching proxy of the same shape, then O17, O15 and Ch. 40. Tip: use the readers–writers pattern (or std::shared_mutex if you write it in C++) for the cache; most bugs are a reader and an evicting writer touching one entry.
