# 1. 오래된 데이터 읽기 : 1년 넘게 전원 없이 둔 데이터는 얼마나 느린가

<div class="glance">
<b>목표</b><span>1년 넘게 전원 없이 있던 이 드라이브의 실제 파일로, 오래 둔 데이터의 읽기가 얼마나 느린지, 그리고 한 번 읽히면 펌웨어가 다시 써서 빨라지는지를 잰다</span>
<b>보는 FTL 개념</b><span>셀 전압의 이동 (charge loss), ECC, read retry, 읽은 뒤 다시 쓰기 (read reclaim), 켜져 있는 동안의 다시 쓰기 (refresh)</span>
<b>지우나?</b><span><b>아니오.</b> 그리고 <b>지우기 전에만 할 수 있다</b> : 한 번 지우면 '1년 넘게 전원 없이 둔 데이터' 는 다시 만들 수 없다</span>
<b>연결</b><span>SATA (실험 3 의 '새 데이터' 스캔과 같은 연결)</span>
<b>시간</b><span>1–2시간 (데이터가 아주 느리게 읽히면 더 걸린다) + 선택 : 하루 뒤 한 번 더 30분</span>
<b>명령</b><span><code>./lab.sh oldfiles /mnt/old840</code>, <code>sudo ./lab.sh scan old 8</code></span>
</div>

## 이 드라이브가 지나온 시간

@@FIG old_history@@

이 실험의 전제는 '데이터를 쓴 지 몇 년' 이 아니라 **'전원 없이 1년 넘게'** 다. 두 가지 시간을 나눠서 본다 :

```table
시간 | 이 드라이브에서 | 그동안 일어나는 일
쓴 뒤 지난 시간 | 파일마다 다르다 : 2018–2024 | 켜져 있던 날에는 펌웨어가 오래된 데이터를 다시 쓸 수 있었다 (펌웨어가 그렇게 한다면)
전원 없이 지낸 시간 | **모든 데이터가 같다** : 2024.12 쯤부터 2026.10.17 까지, 1년 이상 | 다시 쓰기는 없다. 전하만 빠져나간다
```

2024.12 는 `hiberfil.sys` 의 마지막 수정 시각으로 짐작한 것이다 : Windows 를 마지막으로 끈 때. `fileage.py` 는 10.17 이전의 가장 늦은 '쓴 날' 을 찾아 이 날짜를 다시 알려 준다.

**2026.10.17 에 다시 연결한 날 일어난 일** (이것이 측정을 바꾼다) :
- Ryu 가 파일 몇 개를 열어 **읽었다.** 오래된 데이터를 읽으면 펌웨어가 그 블록을 새 자리에 다시 쓸 수 있다 (읽으며 오류가 많았던 블록을 옮기는 것은 흔한 동작이다 : read reclaim). 그러면 그 파일들은 더는 '1년 넘게 둔 데이터' 가 아니다.
- Ryu 가 파일 몇 개를 새로 **썼다** (커널 통계로 약 17.6 MB). 이 파일들은 **막 쓴 데이터** 다 : 같은 드라이브, 같은 파일 시스템, 같은 읽기 경로에서 '나이만 다른' 비교 기준이 된다.
- 그날 드라이브는 몇 시간 켜져 있었다. 켜져 있는 동안 펌웨어가 백그라운드에서 오래된 데이터를 고쳐 쓰기 시작했을 수 있다.

<div class="warn" markdown="1">
**되도록 빨리 한다.** 드라이브가 켜져 있는 시간이 길수록, 펌웨어가 오래된 데이터를 다시 써서 '1년 넘게 둔 데이터' 가 줄어들 수 있다. 실험 0 (준비) 을 마치면 다른 일 없이 바로 이 실험을 한다.
그때까지 이 파티션을 파일 관리자로 열지 않는다 (썸네일 · 미리 보기가 오래된 데이터를 읽는다).
</div>

## 왜 오래 둔 데이터가 느려지나

NAND 셀은 전하 (전자) 를 가두어 데이터를 기억한다. TLC 는 셀 하나에 3비트를 담으려고 전압을 **8단계** 로 나눈다. 읽을 때는 그 사이에 놓은 기준 전압 7개와 비교한다.

@@FIG old_states_fresh@@

시간이 지나면 가둔 전자가 조금씩 빠져나간다. 전압이 높은 (전자가 많은) 상태일수록 더 많이 빠지고, 봉우리는 왼쪽으로 밀리며 넓어진다. 기준 전압을 넘어간 셀은 틀린 값으로 읽힌다. 전원이 있든 없든 빠져나가지만, **전원이 있을 때만** 펌웨어가 데이터를 읽어 보고 새로 쓸 수 있다.

@@FIG old_states_drift@@

틀린 비트는 ECC (오류 정정 부호) 가 고친다. 그러나 오류가 ECC 가 고칠 수 있는 수보다 많으면, 컨트롤러는 **기준 전압을 옮겨 가며 다시 읽는다** (read retry). 다시 읽을 때마다 페이지 읽기 시간 (TLC 에서 수십 µs 이상) 이 더해진다.

@@FIG old_retry@@

840 EVO 는 2014년, 오래된 데이터의 읽기 속도가 새 데이터의 몇 분의 일로 떨어지는 문제로 널리 알려졌다. Samsung 은 펌웨어로 대응했다 ([0. 준비](/old-ssd-experiments/0-setup/) 의 펌웨어 설명 참고). 그 대응의 하나가 '켜져 있는 동안 오래된 데이터를 다시 쓰기' 로 알려져 있는데, **그것은 전원이 없으면 일어날 수 없다.** 그래서 1년 넘게 꺼져 있던 이 드라이브는 펌웨어 버전과 상관없이 좋은 실험 대상이다.

<div class="check" markdown="1">
**이미 보이는 단서.** 2026.10.17 아침 다시 연결한 뒤 커널 통계 (`/proc/diskstats`) 에 따르면, 2.8 GB 를 읽는 동안 디스크가 **40분** 바빴다 : 약 1.2 MB/s. Ryu 가 연 파일들과 파일 관리자 · 썸네일이 읽은 것이고, 어떤 데이터였는지 모르니 측정은 아니다. 그래도 가설과 같은 쪽을 가리킨다.
</div>

## 측정 방법

두 가지를 잰다.

**A. 파일별 (`fileage.py`)** : 파일마다 '데이터를 쓴 날' 과 '그 뒤 읽혔는지' 를 알 수 있으니, 나이 · 이력과 속도를 바로 짝지을 수 있다.

@@FIG old_method@@

- '쓴 날' = NTFS **생성 시각** 과 **수정 시각** 중 늦은 쪽. 설치 프로그램은 파일의 수정 시각을 원본 날짜로 남기는 일이 많아서, 이 디스크에 실제로 쓴 날은 생성 시각이 더 정확하다.
- 파일을 세 무리로 나눈다 :

```table
무리 | 기준 | 몇 개 | 무엇을 보나
`new` | 쓴 날이 2026.10.17 이후 | 1 MiB 이상인 것 전부 (최대 25개) | 비교 기준 (H1)
`read` | 그 전에 썼지만 접근 시각 (`atime`) 이 10.17 이후 | 16 MiB 이상, 최대 25개 | 한 번 읽힌 뒤 다시 쓰였나 (H5)
`old` | 그 밖 : 마지막으로 켜졌을 때 그대로 | 16 MiB 이상, 해마다 25개 (무작위, 같은 seed) | 본 측정 (H2–H4)
```

- 접근 시각은 마운트가 기록할 때만 믿을 수 있다 (Linux 의 기본 `relatime` 은 기록한다). 10.17 에 읽었는데 기록되지 않은 파일은 `old` 에 섞인다 : `old` 안에 유난히 빠른 점이 있으면 그런 파일일 수 있다.
- 파일마다 앞 16 MiB 만 읽는다. 순서는 섞는다 : 측정 중 드라이브 상태가 변해도 특정 해 · 무리에만 몰리지 않게.
- 읽기 전에 `posix_fadvise(DONTNEED)` 로 그 파일의 페이지 캐시를 버린다. 그래야 RAM 이 아니라 드라이브를 잰다.
- 끝에 **가장 느렸던 `old` 10개를 한 번 더 읽는다** (`fileage-reread.csv`, H6). 같은 데이터를 두 번 읽는 것은 이 10개뿐이다.
- **빼는 파일** : 할당된 크기가 길이보다 작은 파일 (sparse, NTFS · WOF 압축). 구멍은 NAND 를 읽지 않고 0 이 나오고, 압축 파일은 CPU 속도를 잰다. 읽다가 실패한 파일은 `fileage-errors.csv` 에 따로 적는다 (0 MB/s 로 넣으면 아주 느린 오래된 파일처럼 보인다). 여기에 `Input/output error` 가 있으면 ECC 로도 못 고친 읽기다 : 그 자체가 결과다.
- 파일은 `ntfs-3g` (FUSE) 를 거쳐 읽으므로 속도의 상한이 SATA (약 540 MB/s) 보다 낮을 수 있다. 그 상한을 `new` 무리가 알려 준다.

**B. 드라이브 전체 (`readscan.py`)** : 256 MiB 구간마다 앞 8 MiB 를 `O_DIRECT` 로 읽는다. 파일 시스템을 거치지 않으므로 EFI · 복구 파티션과 빈 공간 (TRIM 되었으면 0) 까지 다 보인다. 결과 = 위치별 속도 지도. 10.17 에 쓴 17.6 MB 와 읽힌 파일은 전체의 아주 작은 부분이라 지도에는 거의 영향이 없다.

## 절차

```
# 0. 준비 페이지의 1–5단계를 마친 상태 : 도구, check, 읽기 전용 마운트 (/mnt/old840)
$ cd ~/Ryu/jonghoon-ryu.github.io/old-ssd-experiments/scripts

# 1. 파일별 측정 (sudo 필요 없음). 파일 목록을 만들고 (출력 없이 몇 분 걸릴 수 있다),
#    무리 · 해마다 몇 개인지와 '전원 없이 지낸 기간' 추정을 출력한 뒤 읽기 시작한다
$ ./lab.sh oldfiles /mnt/old840

# 2. 드라이브 전체 지도 : 256 MiB 마다 8 MiB (전체의 1/32), 읽기만
$ sudo ./lab.sh scan old 8

# 3. 끝나면 Claude 에게 알리기

# 4. (선택, H7) 컴퓨터와 드라이브를 그대로 켜 두고 (마운트도 그대로, 아무것도 열지 않고) 하루 뒤 :
$ ./lab.sh oldfiles /mnt/old840 --seed 2 --reread 0
```

4는 다른 seed 로 **처음 읽는 다른 파일들** 을 고른다. 1에서 읽은 파일은 이미 '한 번 읽힌' 상태라 다시 재면 안 된다. 4를 할 거라면, 그 전까지 백업 복사도 미룬다.

<div class="warn" markdown="1">
- 위의 두 번 읽기 (H6) 말고는 **같은 데이터를 여러 번 읽지 않는다.** 그래서 백업 복사도 이 실험 **뒤에** 한다.
- 중간에 멈추면 (Ctrl+C) 그때까지의 CSV 는 남는다. 다시 돌릴 때는 다른 `--seed` 로 다른 파일을 고른다 : `./lab.sh oldfiles /mnt/old840 --seed 3`.
- 너무 오래 걸리면 (1 MB/s 근처라면 파일별 측정만 30–50분) 그것 자체가 결과다. 진행 줄에 무리 · 날짜 · MB/s 가 계속 나온다.
</div>

## 결과

<div class="result" markdown="1">
**2026.10.18 08:53 – 09:27** (SATA, 읽기 전용 마운트). 결과 폴더 : `20261018-085307-oldfiles`, `20261018-092257-scan-old`.

### 한 줄 요약

**드라이브 전체가 데이터를 아주 느리게 읽는다 : 데이터가 있는 곳은 약 9 MB/s (정상의 1/50), 비어 있는 곳은 400–520 MB/s.** 데이터의 나이와는 상관이 없었다. 읽기 오류는 하나도 없었다.

### A. 파일별 (`fileage.py`)

612개의 큰 파일 (16 MiB 이상) 중 160개를 읽었다 : `new` 12개, `old` 148개 (해마다 최대 25개). `read` 무리는 0개였다 (10.17 에 연 파일은 모두 16 MiB 보다 작았다). '전원 없이 지낸 기간' 추정 : 마지막 쓰기 2024.12.08 → **677일**.

![파일마다 쓴 날과 읽기 속도](/old-ssd-experiments/1-old-data/age.png)

```table
무리 | 파일 수 | 읽기 속도 중앙값 | 범위
`new` (10.17 에 씀, 1–4 MiB) | 12 | 3.4 MB/s | 1.8 – 5.6
`old` 2011–2018 | 27 | 3.3 – 7.1 MB/s (해마다) | 1.9 – 7.8
`old` 2019–2024 | 113 | 4.0 – 6.3 MB/s (해마다) | 1.0 – 15.5
`old` 전체 | 140 | **4.7 MB/s** | 1 MiB 하나에 중앙값 0.47초, 가장 길게 1.55초
```

- 8개는 1,400–2,200 MB/s 로 읽혔는데, 드라이브가 아니라 RAM 이다 : Windows 의 `WinSxS` 는 같은 파일을 여러 이름 (hard link) 으로 두는데, 다른 이름으로 이미 읽은 데이터가 페이지 캐시에 남아 있었다. 그림과 표에서 뺐고, `fileage.py` 는 이제 hard link 를 한 번만 센다.
- **H1 (새 파일은 빠르다) : 아니다.** 어제 쓴 파일도 3.4 MB/s 다. 다만 이 파일들은 작아서 (1–4 MiB) 파일마다 드는 고정 비용의 몫이 크고, 어제 쓴 데이터가 어디에 어떻게 쓰였는지 (SLC 버퍼 → TLC) 도 모른다.
- **H2 (오래 둔 데이터는 느리다) : 그렇다, 그러나 모두 느리다.** 정상 SSD 라면 이 경로 (`ntfs-3g`) 로도 100 MB/s 이상이 나온다.
- **H3 (오래 썼을수록 더 느리다) : 아니다.** 2011년 파일과 2024년 파일의 중앙값이 비슷하다 (그림의 빨간 선이 평평하다). 차이를 만드는 것은 '쓴 해' 가 아니라 모든 데이터가 함께 겪은 677일인 것으로 보인다.
- **H4 (read retry) : 그렇다는 쪽.** 1 MiB 읽기 하나가 0.5–1.5초 걸린다. 오류 없이 오래 걸리는 것은 기준 전압을 바꿔 가며 다시 읽는 모습과 맞는다. SMART 187 · 195 는 읽기 앞뒤 모두 0.

### Windows 가 남긴 기록

Ryu 에 따르면, 이 드라이브는 Windows 부팅 드라이브였다. 가끔 블루 스크린이 떠서 새로 PC 를 조립했고, 이 SSD 는 그 뒤로 쓰지 않고 두었다. 그러다 심심해서 이 SSD 로 실험해 보기로 했다. 그래서 드라이브에 남아 있는 Windows 의 시스템 로그 (`System.evtx`, 2022.06 – 2024.12) 를 읽어 보았다 (읽기 전용으로 복사한 뒤 `python-evtx` 로).

```table

블루 스크린 (event 1001, BugCheck) | 11번 | 코드가 9가지 : `1A` · `D1` · `FC` · `3B` ×3 · `0A` · `50` · `139` · `7F` · `1E`. 디스크가 원인이면 흔히 보이는 `7A` (KERNEL_DATA_INPAGE_ERROR) · `77` · `F4` 는 없다
```

**블루 스크린의 원인은 이 SSD 가 아니었을 가능성이 크다.** 그때 이 드라이브는 오류 없이 읽혔고, 블루 스크린 코드는 여러 가지가 섞여 있다 : 보통 메모리 (RAM) · 드라이버 · 다른 하드웨어를 먼저 의심하는 모습이다. 지금의 극단적인 느림은 **전원 없이 지낸 677일 동안** 생긴 것으로 보인다.
