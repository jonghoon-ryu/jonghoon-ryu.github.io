# 부록 B. 완료 경로 — 위로 올라가는 신호

튜토리얼 4~8단계는 요청이 **내려가는** 길이었다. 이 부록은 flash 연산이 끝난 뒤 그 소식이 **올라가서** 호스트의 통계가 바뀌기까지를 따라간다. 이 길을 모르면 "왜 응답 시간이 이 값인가", "왜 CQ 가 …" 같은 질문에 답할 수 없다.

- 같은 transaction 완료에 **네 핸들러가 모두 깨어난다.** AMU · GC_WL · 캐시는 자기와 상관없는 출처면 첫 줄에서 돌려보낸다(`if (transaction->Source != …) return;`). `Transaction_Source_Type` 이 `USERIO · CACHE · MAPPING · GC_WL` 네 종류다. **TSU 의 핸들러는 본문이 비어 있다** — "transaction 을 만든 쪽이 처리한다" 는 주석뿐이고, TSU 가 다음 명령을 내보내는 계기는 채널이 idle 이 되는 신호(`handle_channel_idle_signal`, `TSU_Base.cpp:50`)다.

## 3. 캐시 모듈 — 요청이 끝났는지 판단

`handle_transaction_serviced_signal_from_PHY` (`Data_Cache_Manager_Flash_Advanced.cpp:357`) 의 구조는 이렇다.

1. 출처가 USERIO · CACHE 가 아니면 무시. USERIO 면 `broadcast_user_memory_transaction_serviced_signal` 로 **호스트 인터페이스의 통계**를 갱신하도록 알린다(Turnaround/Execution/Transfer/Waiting 평균이 여기서 쌓인다 — [통계](/ftl-visual-simulator/reference/mqsim-code-analysis/big-picture/statistics/)).
2. **읽기**: update read(부분 쓰기용으로 매핑 모듈이 만든 읽기)면 `RelatedWrite->RelatedRead = NULL` 로 연결만 끊고 끝. 아니면 `Transaction_list.remove` 후 `is_user_request_finished` 가 참이면 `broadcast_user_request_serviced_signal`. READ_CACHE · WRITE_READ_CACHE 이면 읽어 온 데이터를 캐시에 넣는 일(slot 삽입, 필요 시 쫓아내기)도 한다.
3. **쓰기**: TURNED_OFF · READ_CACHE 이면 읽기와 같이 완료 판정. WRITE_CACHE 이면 이 신호는 **요청 완료와 무관**하다(요청은 이미 DRAM 쓰기에서 끝났다) — 대신 `back_pressure_buffer_depth` 를 줄이고, 그 LPA 의 slot 이 아직 같은 데이터(타임스탬프가 같거나 더 오래됨)이면 `Remove_slot` 으로 **slot 을 비운다**. 이어서 `waiting_user_requests_queue_for_dram_free_slot` 에서 기다리던 요청을 DRAM 에 받아 준다(back-pressure 한도를 넘으면 중단).

`is_user_request_finished` 의 조건은 `Transaction_list.size() == 0 && Sectors_serviced_from_cache == 0` 이다(`Data_Cache_Manager_Base.h:62`). 즉 flash 쪽 transaction 이 전부 끝나고, DRAM 에서 서비스할 몫도 끝나야 한다.

## 4. 호스트 인터페이스 — `Handle_serviced_request`

`Input_Stream_Manager_NVMe::Handle_serviced_request` (`Host_Interface_NVMe.cpp:98`) 는 이름과 달리 **다섯 가지 일**을 한다.

| 순서 | 일 | 이유 |
|---|---|---|
| ① | `Waiting_user_requests.remove`, `On_the_fly_requests--` | 이 요청을 SQ 에서 처리 중인 목록에서 뺀다 |
| ② | 읽기면 `Send_read_data` — 읽은 데이터를 호스트 메모리 `PRP_entry_1` 로 PCIe 쓰기 | 읽기 데이터는 완료 통지보다 **먼저** 간다 |

## 5. 호스트로 돌아가기

`PCIe_Root_Complex::Write_to_memory` (`PCIe_Root_Complex.cpp:11`) 가 PCIe 쓰기 메시지를 받는다. 주소가 `DATA_MEMORY_REGION` 이상이면 **읽기 데이터**라 그냥 버린다(스탠드얼론 모드에서는 데이터 내용을 옮기지 않는다). 그보다 작으면 CQE 이고, `SQ_ID` 로 flow 번호를 구해서 `IO_Flow::NVMe_consume_io_request` 를 부른다. SATA 면 `sata_hba->SATA_consume_io_request`.

`IO_Flow_Base::NVMe_consume_io_request` (`IO_Flow_Base.cpp:247`) 에서 두 시간이 정해진다.

```cpp
device_response_time = Simulator->Time() - request->Enqueue_time;   // SQ 에 들어간 순간부터
request_delay        = Simulator->Time() - request->Arrival_time;   // 호스트가 요청을 만든 순간부터
```

- `Device_Response_Time` 은 **SQ 에 넣은 뒤**부터, `End_to_End_Request_Delay` 는 **요청을 만든 뒤**부터다. 호스트 쪽 큐가 막혀 요청이 SQ 에 늦게 들어가면 두 값이 벌어진다. ([통계](/ftl-visual-simulator/reference/mqsim-code-analysis/big-picture/statistics/) 문서의 "SSD 가 요청을 받아서부터" 가 이 뜻이다.)
- 이어서 **다음 요청을 만든다**: `IO_Flow_Synthetic::NVMe_consume_io_request` (`IO_Flow_Synthetic.cpp:169`)가 `IO_Flow_Base` 를 부르고, CQ head 를 갱신한 뒤, `QUEUE_DEPTH` generator 이면 `Generate_next_request` → `Submit_io_request` 로 새 요청을 낸다(총 개수 · 정지 시각에 닿으면 `NULL`). 그래서 *완료가 새 요청을 부르는* 닫힌 루프이고, 완료가 늦으면 요청도 늦게 생긴다.

## 6. 시간으로 풀어 보기 — 쓰기 20번 실험

[부록 C](/ftl-visual-simulator/reference/mqsim-code-analysis/tutorial/appendix-debugging/)의 `tiny.xml`(캐시 끔) 결과: `Device_Response_Time` = **854 µs**. 이 값은 다음과 같이 풀린다.

| 구간 | µs | 근거 |
|---|--:|---|
| 요청 도착 → 매핑 읽기 발행 | 2.5 | PCIe · 쪼개기 · CMT 조회 |
| 매핑 page 읽기 | 76.8 | tR 75 + 전송 (`Issued_Flash_Read_CMD_For_Mapping = 20`) |
| 데이터 program | 774.9 | tPROG 750 + 전송 |
| 합계 | **854.3** | 실측 (한 줄씩 보는 법은 [부록 C](/ftl-visual-simulator/reference/mqsim-code-analysis/tutorial/appendix-debugging/) 의 `DEBUG` 출력) |

**왜 캐시를 켜면 43 µs 가 되는가**: 같은 쓰기를 `WRITE_CACHE` 로 보내면(`tinycache.xml`) DRAM 쓰기가 끝나는 순간 요청이 완료되어 `Device_Response_Time` 이 **43 µs** 로 줄고, 뒤에서 flash program 은 그대로 20번 일어난다(`Issued_Flash_Program_CMD = 20`). 호스트가 보는 시간과 flash 가 쓰는 시간이 갈라지는 지점이다.
