## 1. 언제 시작하나

호출 지점은 두 곳이다.

1. **write frontier 가 가득 차서 새 free block 을 받은 직후** (`Flash_Block_Manager.cpp:33`, GC 용 frontier 는 `:52`). 쓰기마다가 아니다.
2. **GC 의 erase 가 끝났는데도 free block 이 부족할 때** (`GC_and_WL_Unit_Base.cpp` 의 ERASE 처리 끝부분).

```cpp
if (free_block_pool_size < block_pool_gc_threshold) { ... }      // GC_and_WL_Unit_Page_Level.cpp:45
```

`block_pool_gc_threshold` 는 생성자에서 `GC_Exec_Threshold × Block_No_Per_Plane` (최소 1)로 계산된다(`GC_and_WL_Unit_Base.cpp:22`). 기본값 0.05 × 2048 = 약 102 — **plane 의 free block 이 102개보다 적어지면** 청소가 시작된다. 이 값은 plane 마다 따로 본다.


<div style="margin-top: 60px;"></div>

## 2. 무엇을 지우나 — victim 선정

정책 switch 가 `gc_candidate_block_id` 를 정한다. 기본 RGA 는 무작위로 `rga_set_size` 개 block 을 뽑아 그중 invalid page 가 가장 많은 것을 고른다.

```cpp
case RGA:
    while (random_set.size() < rga_set_size) {
        block_id = random_generator.Uniform_uint(0, block_no_per_plane - 1);
        if (진행 중인 erase 가 아니고 && is_safe_gc_wl_candidate(pbke, block_id))
            random_set.insert(block_id);
    }
    gc_candidate_block_id = (random_set 중 Invalid_page_count 가 가장 큰 것)
```

`is_safe_gc_wl_candidate()` (`GC_and_WL_Unit_Base.cpp:222`)가 **후보가 될 수 없는 block** 을 걸러낸다.

- 현재 write frontier(`Data_wf` · `GC_wf` · `Translation_wf`) — 지금 쓰고 있는 block 이다
- 진행 중인 program 이 있는 block
- 이미 GC/WL 중인 block

정책을 고른 뒤에도 두 가지 점검이 남는다. `Current_page_write_index == 0` 이거나 `Invalid_page_count == 0` 이면 **지울 게 없으므로 그냥 돌아간다** — 이 GC 기회는 건너뛴다. 그리고 정책마다 후보가 안전한지 확인하는 정도가 달라서, 원본에는 후보를 제대로 검증하지 않는 경로들이 있었다([GC victim 관련 버그](/ftl-visual-simulator/reference/code-change/bug-list/rga-incomplete-block-bug/)).

## 3. GC 의 transaction 만들기

```cpp
block_manager->GC_WL_started(gc_candidate_address);               // 상태 기계: 경쟁 방지
pbke->Ongoing_erase_operations.insert(gc_candidate_block_id);
address_mapping_unit->Set_barrier_for_accessing_physical_block(gc_candidate_address);  // block 잠금

if (block_manager->Can_execute_gc_wl(gc_candidate_address)) {    // 진행 중인 사용자 I/O 가 없다면
    Stats::Total_gc_executions++;
    gc_erase_tr = new NVM_Transaction_Flash_ER(...);
    for (pageID ...) if (Is_page_valid(block, pageID)) {
        gc_read  = new NVM_Transaction_Flash_RD(... 그 page 의 PPA ...);
        gc_write = new NVM_Transaction_Flash_WR(... NO_LPA, NO_PPA ...);   // 아직 목적지 미정
        gc_write->RelatedErase = gc_erase_tr;  gc_read->RelatedWrite = gc_write;
        tsu->Submit_transaction(gc_read);          // read 만 제출한다
        gc_erase_tr->Page_movement_activities.push_back(gc_write);
    }
    tsu->Submit_transaction(gc_erase_tr);
    tsu->Schedule();
}
```

- **block 을 잠근다.** GC 가 끝날 때까지 사용자 요청이 이 block 을 건드리지 못한다. 옮기는 page 의 LPA 도 잠긴다(`Locked_LPAs`).
- **사용자 I/O 가 진행 중이면 지금은 시작하지 않는다.** 이 block 에 읽기·쓰기가 아직 돌고 있다면(`Can_execute_gc_wl` 이 false), 그 I/O 들이 끝나는 완료 신호에서 조건이 풀릴 때 GC 가 시작된다(`GC_and_WL_Unit_Base::handle_transaction_serviced_signal_from_PHY` 의 USERIO 분기).
- **valid page 마다 read 와 write 한 쌍.** write 는 **목적지를 아직 모른다.** 읽기가 끝나야 그 LPA 가 무엇인지 알 수 있어서, 읽기가 끝난 뒤에 write 의 목적지를 정해 제출한다.
- **erase 는 모든 이동이 끝나야 서비스된다.** `Page_movement_activities` 가 비어야 TSU 가 erase 를 내린다(`TSU_Base.h:112`).

GC 의 각 단계는 PHY 의 "트랜잭션 완료" 신호를 `GC_and_WL_Unit_Base::handle_transaction_serviced_signal_from_PHY()` (`GC_and_WL_Unit_Base.cpp:42`)가 받아 다음 단계로 넘긴다.

| 끝난 transaction | 이 함수가 하는 일 |
|---|---|
| **GC read** (valid page 를 읽음) | 그 LPA 의 **현재 매핑**을 조회해 방금 읽은 PPA 와 같은지 확인한다 (읽는 사이 덮어쓰이지 않았는가). 같으면 write 의 LPA·bitmap 을 채우고 `Allocate_new_page_for_gc()` 로 **GC_wf block 의 새 page** 를 받아 매핑을 바꾼 뒤 write 를 제출한다 |
| **GC write** | LPA 의 잠금을 푼다(`Remove_barrier_for_accessing_lpa`). 이동 목록에서 이 write 를 뺀다 |
| **erase** | 장부 정리 → `Add_erased_block_to_pool()` 로 **erase 횟수를 올리고 free pool 에 되돌린다** → 정적 마모평준화 검사 → 대기 중이던 쓰기 재개 → 아직 부족하면 `Check_gc_required()` 한 번 더 |

한 가지 눈여겨볼 점: GC 는 **쓰기를 만든다.** 이동하는 page 하나하나가 flash program 이다. 이것이 write amplification 의 근원이고, 이 프로젝트의 시뮬레이터가 "WAF" 로 보여 주는 숫자의 정체다 — (호스트 쓰기 + GC 이동 쓰기) ÷ 호스트 쓰기.
