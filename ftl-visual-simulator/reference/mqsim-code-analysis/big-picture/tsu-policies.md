# TSU 스케줄러 정책

**TSU(Transaction Scheduling Unit)** 는 FTL 이 물리 주소까지 정해서 넘긴 transaction 을 "어느 칩에, 언제, 어떤 묶음으로" 내릴지 정하는 부품이다(`ssd/TSU_*.cpp`). [튜토리얼 8단계](/ftl-visual-simulator/reference/mqsim-code-analysis/tutorial/step8-tsu-chip/)가 흐름을 따라갔다면, 여기서는 **정책이 무엇이 다른지**와 **묶어서 내리는 규칙**을 정리한다.


<div style="margin-top: 60px;"></div>

## 1. 선택할 수 있는 정책

`Transaction_Scheduling_Policy` 가 `SSD_Device` 생성자(`exec/SSD_Device.cpp:139`)에서 구현을 고른다.

| 값 | 클래스 | 상태 |
|---|---|---|
| `OUT_OF_ORDER` | `TSU_OutOfOrder` | 동작. 사용자 큐 하나, 도착 순서(칩별) — Sprinkler(HPCA 2014)식 비순차 실행 + 서스펜드 |
| `PRIORITY_OUT_OF_ORDER` | `TSU_Priority_OutOfOrder` | **기본값.** 위에 flow 우선순위 class 를 얹은 것 |
| `FLIN` | `TSU_FLIN` | **코드 전체가 주석 처리되어 있다** (`TSU_FLIN.h` · `TSU_FLIN.cpp` 가 `/* … */`, `SSD_Device.cpp` 의 생성 부분도 주석). enum 값만 남아 있어서 고르면 `"No implementation is available …"` 예외가 난다 |

**FLIN 은 선택할 수 없다.** 원본 MQSim 문서나 논문에 FLIN(공정성 중심 스케줄러)이 나오지만, 지금 저장소에서는 쓸 수 없다.

> 샘플 시나리오 2 에서 flow 0 을 URGENT 로 두면 HIGH 인 flow 1 보다 IOPS 가 높고 응답이 짧게 나온 것이 이 규칙 때문이다([튜토리얼 1단계](/ftl-visual-simulator/reference/mqsim-code-analysis/tutorial/step1-run-and-main/)).

## 6. 이 프로젝트에서의 의미

- 시뮬레이터의 **"명령 일시정지(suspend)"** 설정은 위의 서스펜드 경로다. 원본에서는 한 번도 작동하지 않았으므로 이 프로젝트가 4개의 결함을 고쳤고, 고친 뒤에는 읽기 지연 차트에서 "가장 느린 읽기"가 줄어드는 것이 보인다([명령 서스펜드가 한 번도 작동한 적이 없던 버그](/ftl-visual-simulator/reference/code-change/bug-list/suspend-resume-deadlock-bug/)).
- GC 가 도는 동안 읽기가 느려지는 이유(긴급 모드에서 GC write/erase 가 읽기를 막음)도 이 순서에서 나온다.
