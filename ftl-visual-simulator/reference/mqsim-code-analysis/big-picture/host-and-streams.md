# 호스트와 stream

호스트 쪽 코드(`host/`, 약 2,100줄)는 "SSD 에 부하를 주는 무대"이다. FTL 과 직접 관계는 적지만, **stream · 논리 주소 분할 · 요청 생성 방식**을 알아야 FTL 의 결과(예: 왜 flow 가 둘이면 쓰기 공간이 반이 되는지)를 해석할 수 있다.

- `workload.xml` 의 **IO flow** 하나는 호스트의 I/O 발생기 하나다. NVMe 에서는 flow 마다 **submission queue / completion queue 한 쌍**이 생기고, SSD 쪽에서는 **stream** 하나가 된다. 큐 0 번은 admin 전용이라 flow 번호에 1 을 더한 큐를 쓴다(`FLOW_ID_TO_Q_ID`, `Host_Defs.h`).
- **자원이 stream 별로 나뉜다.** `Logical_Address_Partitioning_Unit` 이 flow 별로 쓸 수 있는 채널 · 칩 · 다이 · 플레인을 정하고, 같은 plane 을 n 개 flow 가 쓰면 각자 그 plane 의 1/n 을 갖는다. 논리 주소 공간도 flow 순서대로 이어 붙여서 나눈다(`utils/Logical_Address_Partitioning_Unit.cpp`).
- **write frontier 도 stream 별**이다(`Data_wf[stream_id]`). 그래서 서로 다른 flow 의 데이터는 같은 block 에 섞이지 않는다 — 이 프로젝트의 "핫/콜드 분리" 실험이 두 flow 로 이를 이용한다.
- 매핑 테이블(`AddressMappingDomain`)도 stream 마다 한 벌이다.

## 4. trace 재생과 우선순위

- **Trace_Based flow** 는 ASCII trace 를 한 줄씩 읽는다. 한 줄은 공백으로 나뉜 **5개 열**이다: 도착 시각, 장치, 주소, 크기, 종류(0 = 쓰기, 1 = 읽기). 시각 단위는 ps/ns/µs 중 하나(`ASCII_Trace_Definition.h`). 도착 시각이 trace 에 박혀 있어서 부하 강도를 trace 가 정한다.
- **우선순위 class** — flow 마다 `URGENT · HIGH · MEDIUM · LOW` 를 줄 수 있다(`Host_Interface_NVMe_Priorities.h`). 스케줄링 가중치는 URGENT = 무한대(항상 먼저), HIGH = 4, MEDIUM = 2, LOW = 1 이다. 이 class 는 요청 → transaction 에 그대로 전달되어 TSU 의 큐 선택에 쓰인다([TSU 스케줄러 정책](/ftl-visual-simulator/reference/mqsim-code-analysis/big-picture/tsu-policies/)).

## 5. 호스트 ↔ SSD 연결: NVMe 와 SATA

| | NVMe | SATA |
|---|---|---|
| 큐 | flow 마다 SQ/CQ 쌍 (multi-queue) | 단일 큐 (NCQ) — stream 이 하나뿐 |
| 입구 | `Host_Interface_NVMe` · `Request_Fetch_Unit_NVMe` | `Host_Interface_SATA` · SATA HBA |
| 명령 가져오기 | doorbell → SSD 가 SQ 를 DMA 로 읽음 (`Queue_Fetch_Size` 개씩) | HBA 가 NCQ 로 전달 |
| 설정 | `IO_Queue_Depth`, `Queue_Fetch_Size` | `SATA_Processing_Delay` |

PCIe 구간의 시간은 `PCIe_Link::estimate_transfer_time()` 이 계산한다. 보낼 byte 수에 TLP 헤더·패킷 오버헤드를 더해서 **레인 수와 레인 대역폭**으로 나눈다(`PCIe_Link.h:44`). 링크는 방향별로 버퍼를 하나 두고 메시지를 **차례로** 보낸다 — 앞 메시지가 가는 동안 뒤 메시지는 기다린다(`PCIe_Link::Deliver`).
