# 이벤트 스케줄러 따라가기 — 알람 목록으로 보는 시뮬레이션

MQSim 같은 discrete-event 시뮬레이터가 **실제로 어떻게 시간을 흘려보내는지**, 작은 예제 하나를 처음부터 끝까지 손으로 따라가며 본다. 코드는 거의 없고 그림 위주다. 같은 내용을 MQSim 코드 기준으로 정리한 문서는 [이벤트 엔진과 시간](/ftl-visual-simulator/reference/mqsim-code-analysis/big-picture/event-engine/)이다.

<div style="margin-top: 60px;"></div>

## 1. 한 문장으로

시뮬레이터는 **알람 목록**을 하나 갖고 있다. 알람마다 *"시각 T 에 X 에게 Y 가 일어났다고 알려라"* 가 적혀 있다. 엔진은 **가장 이른 알람을 꺼내 시계를 그 시각으로 맞추고**, X 가 반응하게 한다. 반응은 대개 **미래의 새 알람을 등록**하는 것이다. 이것 말고는 아무것도 시뮬레이션을 움직이지 않는다 — 시계가 1 씩 똑딱이며 흐르는 일은 없다.

## 3. 명령은 어디서 오나 — host 도 알람으로 움직인다

정리하면:

- **누가 시작하나?** host 객체의 **시작 알람**(t = 1 ns)이 첫 요청 4개를 만든다. 그 뒤로는 **완료 알람** 안에서 다음 요청이 만들어진다 — 엔진이 따로 "새 명령" 을 넣는 일은 없다.
- **순서와 간격이 미리 정해져 있나?** QUEUE_DEPTH 에서는 **아니다.** 다음 요청의 시각은 앞 요청이 끝나는 시각이 정하고, 읽기/쓰기와 주소는 그 순간 난수(seed 고정)로 정한다. 그래서 목록은 없지만 같은 설정이면 결과는 매번 똑같다. 미리 정해진 순서를 쓰려면 TRACE 방식(trace 파일)을 쓴다.
- **어떻게 가져가나?** host 는 요청을 메모리의 submission queue 에 넣고 doorbell 을 PCIe 로 SSD 에 쓴다. 그 doorbell 이 도착하는 **알람**에서 SSD 가 SQ 항목을 **하나씩** PCIe 로 읽어 온다(쓰기면 데이터도 한 번 더). 끝나면 완료 항목을 host 로 보내고, 그 완료 알람에서 host 가 다음 요청을 만든다.

| 알람 목록 | `EventTree` (시각을 키로 한 red-black tree, 같은 시각은 한 노드에 줄 세움) |

| 가장 이른 알람 꺼내 실행 | `Engine::Run_next_event_group()` — 같은 시각 알람을 모두 처리 |
| 대상이 반응 | 각 객체의 `Execute_simulator_event()` |
| 대기열 | 스케줄러(TSU)의 칩별 큐, FTL 의 빈 공간 대기 목록 등 |
| 알람 목록이 빔 = 끝 | `Count == 0` 이면 루프 종료 |

자세한 설명과 실제 쓰기 하나의 이벤트 사슬은 [이벤트 엔진과 시간](/ftl-visual-simulator/reference/mqsim-code-analysis/big-picture/event-engine/)에 있다.
