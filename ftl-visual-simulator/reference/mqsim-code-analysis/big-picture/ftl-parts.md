# FTL 의 부품들과 자료구조

- 이 때문에 "매핑 miss" 가 **실제 flash read** 를 만든다. 매핑 자료도 결국 flash 공간과 시간을 쓴다.

핵심은 세 가지이다.

- **free pool 이 erase 횟수로 정렬돼 있다.** 새 write frontier 를 고를 때 `begin()` 을 뽑으면 가장 덜 닳은 block 이 나온다. 별도 로직 없이 자료구조의 정렬이 **dynamic wear leveling** 을 만든다(`Get_a_free_block`, `Flash_Block_Manager_Base.cpp:105`).
- **write frontier 가 stream 마다 셋이다.** 사용자 쓰기(`Data_wf`)와 GC 가 옮겨 쓰는 쓰기(`GC_wf`)가 서로 다른 block 에 쌓인다. 이 구조 덕분에 오래 살아남은 데이터(GC 가 옮긴 것)와 새 데이터가 어느 정도 분리된다.
- **block 마다 상태 필드가 있다.**

| `Block_Pool_Slot_Type` 필드 | 의미 |
|---|---|
| `Current_page_write_index` | 지금까지 쓴 page 수 = 다음에 쓸 page 번호 |
| `Invalid_page_bitmap` | page 별 비트: 0 = valid, 1 = invalid |
| `Invalid_page_count` | invalid page 수 (GC 가 victim 을 고를 때 본다) |
| `Erase_count` | 지운 횟수 (마모 평준화의 기준) |
| `Current_status` | IDLE / GC_WL / USER / GC_USER … (GC 와 사용자 I/O 의 경쟁 방지용 상태 기계) |
| `Has_ongoing_gc_wl` | 지금 GC/WL 대상이다 |
| `Ongoing_user_read_count` · `…_program_count` | 이 block 에 진행 중인 사용자 I/O 수 — 0 이 돼야 GC 를 시작할 수 있다 |
| `Stream_id` | 어느 flow 의 데이터를 담고 있나 |
