# GC 알고리즘 — victim 을 고르는 7가지 방법

GC(garbage collection)는 **빈 block 이 모자라면, block 하나를 골라 그 안의 valid page 를 다른 곳으로 옮기고 block 을 지워서 빈 block 을 만드는 일**이다. 이때 "어느 block 을 지울까" 를 정하는 규칙이 **GC 알고리즘**(MQSim 의 `GC_Block_Selection_Policy`)이다. 고른 block 을 **victim** 이라고 부른다.

이 페이지는 MQSim 의 일곱 가지 알고리즘이 각각 어떤 block 을 고르는지, 그리고 시뮬레이터 기본 설정에서 실제로 어느 쪽이 싼지를 정리한다. 코드는 `ssd/GC_and_WL_Unit_Page_Level.cpp` 의 `Check_gc_required()` 한 함수에 다 들어 있다. 한 줄씩 따라가는 설명은 [튜토리얼 9단계](/ftl-visual-simulator/reference/mqsim-code-analysis/tutorial/step9-gc/)에 있다.

- **언제:** plane 의 free block 수가 `block_pool_gc_threshold` 보다 **작아지면** 시작한다. 이 값은 `GC_Exec_Threshold × plane 당 block 수` 를 내림한 것인데, 최소 1, 그리고 한 plane 에서 동시에 돌 수 있는 GC 수(`max_ongoing_gc_reqs_per_plane`, 이 프로젝트에서는 3) 이상이 되도록 끌어올린다. 시뮬레이터 기본값(GC 임계값 30%, block 12개)이면 `floor(0.3 × 12) = 3` 개다.
- **비용:** GC 가 하는 일의 대부분은 ③ valid page 옮기기다. victim 에 valid page 가 적을수록(= invalid page 가 많을수록) 옮길 게 적어서 싸다. 그래서 거의 모든 알고리즘이 결국 "invalid 가 많은 block" 을 찾으려 하고, **차이는 얼마나 열심히 찾느냐**와 **무엇을 더 보느냐**에 있다.
- **어떤 알고리즘이든 공통:** 쓰기 위치 block(`Data_wf` · `GC_wf` · `Translation_wf`), 아직 program 이 끝나지 않은 block, 이미 GC 중인 block 은 고를 수 없다(`is_safe_gc_wl_candidate()`). 고른 block 이 비어 있거나 invalid page 가 0 이면 그 GC 기회는 그냥 넘어간다.

| 알고리즘 | 고르는 방법 | 비교하는 block 수 | 장점 / 약점 |
|---|---|---|---|
| **Greedy** | 가득 찬 block 을 전부 보고 invalid 가 가장 많은 것. 동률이면 번호가 낮은 block | 전부 | 매번 가장 싼 victim. 대신 block 이 수천 개면 매번 전부 훑는 비용이 크고, 막 쓴 hot block 을 너무 일찍 고를 수 있다 |
| **RGA** (기본값) | 가득 찬 block 을 무작위로 `log₂(block 수)` 개 뽑아 그중 invalid 가 가장 많은 것 (Randomized Greedy) | log₂N 개 (block 12개면 3개) | Greedy 에 가까운 품질을 훨씬 적은 비교로. 뽑힌 몇 개 안에서만 최선이다 |
| **Random** | 쓰기 위치만 아니면 아무 block | 1 개 | 가장 단순. 빈 block 이나 valid 투성이 block 도 뽑힌다 — 빈 block 이면 그 GC 기회를 건너뛴다 |
| **Random-p** | 가득 찬 block 중 무작위 | 1 개 | Random 보다 낫지만 invalid 개수는 안 본다 |
| **Random-pp** | 가득 찬 block 중 invalid 가 `rho × page 수` 이상인 것 중 무작위 | 1 개 | 하한이 있어서 너무 비싼 victim 은 피한다. `rho` 는 flow 의 초기 점유율에서 오는데 시뮬레이터에서는 0 이라 **Random-p 와 같게 동작**한다 |
| **FIFO** | 가장 먼저 할당된(가장 오래된) 가득 찬 block 부터 | 큐 맨 앞 | invalid 개수와 무관하게 돌아가며 지워서 마모가 고르다. 대신 비싼 victim 을 고를 때가 많다 |
| **Cost-Benefit** | `(1−u)/2u × 나이` 가 가장 큰 것 (아래 3절) | 전부 | 지금 싼 정도와 "앞으로도 안 바뀔지" 를 함께 본다. hot/cold 가 섞인 workload 에 강하다 |

**원본 MQSim 과 다른 점.** Cost-Benefit 은 원본에 없어서 이 프로젝트가 추가했다. FIFO 는 원본에서 큐 맨 앞을 확인 없이 꺼냈는데, 빈 큐 · 위험한 block · 끝없이 커지는 큐 문제가 있어서 고쳤다(버그 #25 · #27). Greedy · RGA · Random 계열도 "검사하지 않은 후보를 그냥 쓰는" 경로가 있어 작은 규모에서 멈추거나 죽었는데, 모두 "안전한 후보가 없으면 이번 GC 를 건너뛴다" 로 고쳤다. 자세한 것은 [원본 MQSim 대비 변경 사항](/ftl-visual-simulator/reference/code-change/upstream-diff/)에 있다.
</div>

## 3. Cost-Benefit 은 왜 나이를 곱하나

<svg viewBox="0 0 980 250" style="font-variant-ligatures:none;width:100%;max-width:980px;height:auto;display:block;margin:1rem auto;" font-family="'IBM Plex Sans KR','IBM Plex Sans','Noto Sans KR','NanumGothic','Apple SD Gothic Neo','Malgun Gothic',sans-serif" role="img" aria-label="Cost-Benefit 점수"><defs><marker id="agccb" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="8" markerHeight="8" orient="auto"><path d="M0,0 L10,5 L0,10 z" fill="#7f8c8d"/></marker></defs><text x="490" y="22" font-size="13" font-weight="700" fill="#2c3e50" text-anchor="middle">Cost-Benefit 의 점수 — &quot;지금 싸다&quot; 와 &quot;앞으로도 안 바뀐다&quot; 를 같이 본다</text><rect x="15" y="50" width="300" height="110" rx="8" fill="#fdedec" stroke="#c0392b" stroke-width="2"/><text x="165.0" y="93.0" font-size="12.5" font-weight="700" fill="#2c3e50" text-anchor="middle">benefit = 1 − u</text><text x="165.0" y="110.0" font-size="11" fill="#4d5656" text-anchor="middle">u = valid 비율 (옮겨야 할 몫)</text><text x="165.0" y="127.0" font-size="11" fill="#4d5656" text-anchor="middle">지우면 얻는 빈 page 비율</text><rect x="340" y="50" width="300" height="110" rx="8" fill="#fdf2e9" stroke="#ca6f1e" stroke-width="2"/><text x="490.0" y="93.0" font-size="12.5" font-weight="700" fill="#2c3e50" text-anchor="middle">cost = 2u</text><text x="490.0" y="110.0" font-size="11" fill="#4d5656" text-anchor="middle">valid page 를 읽고(u) 다시 쓰는(u)</text><text x="490.0" y="127.0" font-size="11" fill="#4d5656" text-anchor="middle">데 드는 일</text><rect x="665" y="50" width="300" height="110" rx="8" fill="#ebf5fb" stroke="#2874a6" stroke-width="2"/><text x="815.0" y="85.0" font-size="12.5" font-weight="700" fill="#2c3e50" text-anchor="middle">× age</text><text x="815.0" y="102.0" font-size="11" fill="#4d5656" text-anchor="middle">block 이 할당된 뒤 흐른 시간</text><text x="815.0" y="119.0" font-size="11" fill="#4d5656" text-anchor="middle">오래 안 바뀐 데이터 = 앞으로도</text><text x="815.0" y="136.0" font-size="11" fill="#4d5656" text-anchor="middle">안 바뀔(cold) 가능성이 큼</text><text x="490" y="192" font-size="12.5" font-weight="700" fill="#2c3e50" text-anchor="middle">score = (1 − u) / 2u × age   →   가장 큰 block 이 victim</text><text x="490" y="216" font-size="11" fill="#4d5656" text-anchor="middle">Greedy 는 앞의 두 칸(invalid 개수)만 본다. 새로 쓴 hot block 은 invalid 가 금방 더 생길 텐데,</text><text x="490" y="233" font-size="11" fill="#4d5656" text-anchor="middle">지금 고르면 곧 무효가 될 page 까지 옮기게 된다 — Cost-Benefit 은 나이를 곱해 그런 block 을 미룬다.</text></svg>

이 식은 log-structured 파일 시스템(LFS, Rosenblum & Ousterhout 1992)의 cost-benefit 정책을 flash 에 맞게 고친 것이다. LFS 는 victim 을 통째로 읽어야 해서 비용을 `1 + u` 로 쳤지만, flash 는 valid page 만 읽고(u) 다시 쓰므로(u) `2u` 가 된다(Kawaguchi 외, 1995).

예를 들어 invalid 가 12개로 같은 block 이 둘이면 Greedy 는 번호가 낮은 쪽을 고르지만, Cost-Benefit 은 **더 오래전에 할당된 쪽**을 고른다. 오래전에 쓴 데이터 중 아직 살아남은 page 는 앞으로도 덮어써지지 않을(cold) 가능성이 크니, 옮겨 놓으면 한동안 다시 옮길 일이 없다. 반대로 방금 쓴 block 은 기다리면 invalid 가 더 늘어나서 나중에 더 싸게 지울 수 있다.

## 4. 시뮬레이터 기본 설정에서는 무엇이 쌀까

GC 시연 기본 설정(칩 2개 · 칩당 block 12개 · OP 20% · GC 임계값 30% · 작업 범위 40% · 읽기 30% · DRAM 캐시 32 page)으로 알고리즘만 바꿔 끝까지 돌린 결과다(`engine/tests/cache/claims.mts`, 2026-10-11).

| 알고리즘 | WAF | GC 실행 횟수 |
|---|--:|--:|
| **Greedy** | **1.34×** | 544 |
| Cost-Benefit | 1.37× | 555 |
| RGA (기본) | 1.38× | 536 |
| FIFO | 1.40× | 536 |
| Random-p | 1.63× | 525 |
| Random-pp | 1.63× | 525 |
| Random | 1.69× | 516 |

- **invalid 를 보는 알고리즘(Greedy · Cost-Benefit · RGA)이 싸고, 무작위 계열이 비싸다.** 교과서와 같은 순서다.
- **RGA 가 Greedy 에 거의 붙는다.** block 12개 중 3개만 비교하는데도 차이가 0.04× 다. 수천 개 block 에서 매번 전부 훑지 않으려고 RGA 가 MQSim 의 기본값인 이유다.
- **FIFO 가 생각보다 괜찮다.** 이 workload 는 작업 범위 안을 무작위로 고르게 덮어써서, 오래된 block 일수록 invalid 도 많기 때문이다. 덮어쓰기가 한쪽에 몰리는 workload 에서는 FIFO 가 훨씬 나빠진다.
- **Random 은 GC 를 가장 적게 한다(516번).** 빈 block 을 뽑으면 그 기회를 건너뛰니까 횟수는 줄지만, 할 때마다 valid 가 많은 block 을 옮겨서 WAF 는 가장 높다. 횟수가 아니라 옮긴 page 수(WAF)로 비교해야 하는 이유다.

<div class="tip" markdown="1">
**block 이 적으면 순위가 쉽게 바뀐다.** 이 데모는 plane 하나에 block 이 12개뿐이라, 한 번의 선택이 다음 GC 들의 상황까지 바꾼다. 같은 실험을 OP 10% · GC 임계값 50% 로 했을 때는 Random 이 2.06× 로 가장 낮고 Greedy 가 2.19× 였다. 작업 범위나 OP 를 바꾸고 직접 돌려 보면 순위가 오르내리는 것을 볼 수 있다.
</div>

## 5. GC 는 사용자 요청과 어떻게 같이 도나

- 시뮬레이터 설정은 `Preemptible_GC_Enabled = false` 라서, MQSim 입장에서는 **GC 가 항상 '긴급 모드'** 다(`GC_is_in_urgent_mode()` 가 늘 true). 칩이 비면 TSU 는 GC 의 읽기 · 쓰기 · erase 를 사용자 요청보다 먼저 내린다. 그래서 GC 가 도는 동안 읽기 지연이 튄다 — [TSU 스케줄러 정책](/ftl-visual-simulator/reference/mqsim-code-analysis/big-picture/tsu-policies/).
- GC 가 page 를 옮기는 동안 그 LPA 는 잠긴다(barrier). 같은 LPA 에 대한 사용자 요청은 옮기기가 끝날 때까지 기다린다 — [GC 와 사용자 I/O 의 경쟁 방지](/ftl-visual-simulator/reference/mqsim-code-analysis/big-picture/concurrency-control/).
- 옮긴 page 는 원래 데이터를 쓴 stream 의 `GC_wf` 로 간다. 그래서 GC 를 거친 오래된 데이터는 새 데이터와 다른 block 에 모인다.
